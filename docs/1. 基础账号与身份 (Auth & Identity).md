基于现有的前端实现，我建议您的用户资料数据库（User Profile）应包含以下字段，分为四个核心维度：

### 1. 基础账号与身份 (Auth & Identity)
这些字段用于登录验证和用户在平台上的唯一标识。

- id : 唯一标识符 (Primary Key, 如 UUID 或自增 ID)。
- username : 登录账号 (Unique)，对应 login.vue 中的输入。
- password_hash : 加密后的密码 ，不可明文存储。
- phone : 手机号 ，移动端应用通常需要的验证方式。
- email : 电子邮箱 ，可选，用于找回密码。
- status : 账号状态 (0: 正常, 1: 禁用, 2: 未激活)。
### 2. 个人基本资料 (Personal Profile)
对应 user.vue 及其头部组件展示的内容。

- nickname : 用户昵称 ，对应页面上的 displayName 。
- avatar_url : 头像地址 ，存储在云存储（如腾讯云 COS）的 URL。
- gender : 性别 (0: 保密, 1: 男, 2: 女)，社交应用必备。
- birthday : 生日 ，用于计算年龄和展示星座。
- bio : 个人简介/签名 ，“怎么称呼你”之外的自我介绍。
- location : 常驻城市 ，方便匹配“附近的搭子”。
- cover_image : 个人主页背景图 ，对应 moment.vue 中的 coverImage 。
### 3. 社交与活动统计 (Social & Activity Stats)
这些字段通常作为冗余字段（或通过关联查询获得）用于展示在 UserDataPanel.vue 。

- friend_count : 好友数量 。
- circle_count : 加入的圈子数量 。
- activity_count : 参与的历史活动总数 。
- moment_count : 发布的动态数量 。
- album_count : 相册照片数量 。
### 4. 资产与系统信息 (Assets & System)
对应 UserStatsPanel.vue 和钱包功能。

- points_huochai : 伙柴值 (积分或活跃度)。
- points_huoka : 伙卡数量 (可能是权益卡或道具)。
- balance : 钱包余额 ，用于支付活动费用。
- created_at : 注册时间 。
- last_login_at : 最后登录时间 。
** 数据库表结构建议 (SQL 示例) **

```
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    nickname VARCHAR(50),
    avatar_url VARCHAR(255),
    phone VARCHAR(20) UNIQUE,
    gender TINYINT DEFAULT 0, -- 0:未知, 1:男, 2:女
    birthday DATE,
    bio VARCHAR(200),
    points_huochai INT DEFAULT 0,
    points_huoka INT DEFAULT 0,
    balance DECIMAL(10, 2) DEFAULT 0.00,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE 
    CURRENT_TIMESTAMP
);
```

通用用户数据库核心字段设计

一套通用用户表设计，覆盖基础身份、账号安全、状态管理、业务扩展四大维度，适配绝大多数B端/C端项目，可按需删减。

一、核心基础字段（必选）

1. 用户ID（user_id）：主键，唯一标识，推荐自增主键/雪花算法ID，避免业务关联风险

2. 账号标识：

◦ 用户名（username）：登录名，唯一，支持自定义/系统生成

◦ 手机号（phone）：唯一，用于登录+验证，需加密存储

◦ 邮箱（email）：唯一，用于登录+找回密码，需加密存储

3. 密码相关：

◦ 密码哈希（password_hash）：不存明文，使用BCrypt/Argon2加密

◦ 密码盐值（salt）：可选，增强密码安全性（部分加密算法内置）

4. 基础信息：

◦ 昵称（nickname）：展示名，可重复

◦ 头像（avatar）：头像URL/存储路径

◦ 性别（gender）：枚举值（0-未知、1-男、2-女）

◦ 生日（birthday）：日期格式，用于年龄计算/生日权益

二、账号安全字段（必选）

1. 账号状态：

◦ 状态（status）：枚举值（0-禁用、1-正常、2-锁定、3-未激活）

◦ 激活状态（is_activated）：布尔值，标记邮箱/手机是否验证

2. 登录安全：

◦ 最后登录时间（last_login_time）：记录最近登录时间

◦ 最后登录IP（last_login_ip）：记录登录IP，用于异常登录检测

◦ 登录失败次数（login_fail_count）：用于密码错误锁定

◦ 锁定时间（lock_time）：账号锁定截止时间

3. 凭证管理：

◦ 刷新令牌（refresh_token）：可选，用于免密登录场景

◦ 令牌过期时间（token_expire）：刷新令牌有效期

三、业务扩展字段（按需选）

1. 身份权限：

◦ 用户类型（user_type）：枚举值（0-普通用户、1-管理员、2-VIP用户）

◦ 角色ID（role_id）：关联角色表，用于RBAC权限控制

◦ 会员等级（vip_level）：0-非会员，1-普通会员，2-高级会员等

2. 业务属性：

◦ 注册渠道（register_channel）：枚举（APP、小程序、H5、第三方登录）

◦ 注册来源（register_source）：记录推广渠道ID，用于数据统计

◦ 第三方关联ID（open_id）：微信/QQ/支付宝等第三方登录唯一标识

3. 运营相关：

◦ 积分（points）：用户业务积分

◦ 余额（balance）：用户账户余额（金额类型，保留2位小数）

◦ 邀请人ID（inviter_id）：关联上级用户ID，用于裂变/分销业务

四、通用系统字段（必选）

1. 创建时间（create_time）：记录用户注册时间，默认当前时间

2. 更新时间（update_time）：记录用户信息最后修改时间，自动更新

3. 创建人（create_by）：可选，记录后台添加用户的管理员ID

4. 删除标记（is_deleted）：逻辑删除标记（0-未删、1-已删），避免物理删除数据丢失

补充设计建议

• 索引优化：对user_id、phone、email、username建立唯一索引，提升查询效率

• 数据加密：手机号、邮箱等敏感字段采用AES加密存储，避免泄露

• 分表考虑：用户量超千万级时，按user_id分表，避免单表数据过大

• 字段适配：C端侧重手机号/第三方登录，B端增加部门ID、工号等字段

在数据库设计中，关于 基础账号与身份 (Auth & Identity) 和 个人基本资料 (Personal Profile) 是合表还是分表，通常取决于项目的规模、安全性要求以及未来的扩展性。

针对您目前的 UnitOne / HiGoer 社交活动项目，我的建议是： 采用“分表设计” (Split Tables) 。

以下是两种方案的对比分析及推荐理由：

### 方案一：分表设计 (推荐方案)
将敏感的账号信息（用于登录和验证）与公开的个人资料（用于展示和社交）分开。

- users 表 (基础账号与身份) : 包含 id , username , password_hash , phone , email , status , created_at 等。
- user_profiles 表 (个人基本资料) : 包含 user_id (关联外键), nickname , avatar_url , gender , bio , location 等。
** 推荐理由 **

1. 安全性 (Security) :
   - 您可以对 users 表设置更严格的访问权限。在查询用户的公开资料时（如在朋友圈 moment.vue 中展示头像和昵称），数据库查询只会触及 user_profiles 表，从而物理隔离了密码哈希等敏感信息。
2. 性能 (Performance) :
   - 登录验证是高频操作，保持 users 表精简（字段少、行宽窄）能显著提升索引效率和查询速度。
3. 扩展性 (Scalability) :
   - 作为一个社交项目，未来您可能会增加很多资料字段（如：兴趣标签、社交账号绑定、个性化配置等）。如果全部塞进一张表，单行数据会变得非常臃肿，影响维护。
### 方案二：单表设计 (合表)
将所有字段放在一张 users 表中。

- users 表 : 包含 id , username , password_hash , nickname , avatar_url , phone ... 等所有字段。
** 适用场景 **

- 快速原型开发 : 如果您目前处于极速开发阶段，合表可以减少一次 JOIN 查询，代码实现更简单。
- 字段极少 : 如果用户资料除了头像和昵称，没有其他任何扩展，合表也是可以接受的。
